# Решения и технологии

Подробности к короткому разделу «Что было непросто» в [README](../README.md).

## Технологии и почему

- **Python и стандартная библиотека.** Для денег `decimal.Decimal`, для командной строки `argparse`. Единственная зависимость `httpx`, и нужна она только для точного подсчёта через API.
- **JSON для таблицы цен**, а не код. Цены меняются чаще, чем логика, и обновить их должно быть можно без правки пакета. У каждой модели в таблице дата сверки и ссылка на страницу с ценами.
- **pytest**, сеть в тестах подменена через `httpx.MockTransport`, ключ не нужен. На Гитхабе тесты идут на Python 3.10 и 3.12 при каждом изменении.

## Деньги нельзя считать во float

Цена открытой модели на Groq 0.075 доллара за миллион токенов, запрос стоит доли цента, и таких запросов тысячи. Во float 0.1 хранится не точно, и ошибка накапливается при сложении. Поэтому цены лежат в JSON строками, читаются в `Decimal`, а число с точкой без кавычек загрузчик отклоняет: оно уже прошло через float при чтении JSON. Округление только при выводе. Тест проверяет, что 10 000 одинаковых запросов дают ровно 0.0105; то же сложение во float даёт 0.010500000000000956.

## Мелкие суммы не должны превращаться в $0.00

Обычное округление до центов показало бы, что прогон на 14 запросов бесплатный. Вывод от доллара и выше идёт с двумя знаками, ниже доллара до шести знаков без лишних нулей.

## Честно про точность подсчёта токенов

Точное число знает только токенизатор модели. У Anthropic он не опубликован, у OpenAI словари токенизатора скачиваются из сети при первом запуске, а нужна была работа без сети. Поэтому `estimate` делает прикидку по классам символов: латиница примерно 4 символа на токен (так пишет OpenAI про английский), кириллица мельче, знаки и эмодзи по токену на символ. Коэффициенты подобраны грубо и не откалиброваны на настоящем токенизаторе, поэтому выбраны с запасом в большую сторону, и в выводе стоит «≈». Для точного числа есть `--exact` через count_tokens API или поле usage в ответе модели.

Пример прикидки (настоящий вывод; ответ посчитан как полные 512 токенов, то есть это верхняя граница):

```text
$ python -m token_counter estimate --model claude-sonnet-4-6 --output 512 --times 14 \
    --text "Достань из обращения клиента номер заказа и телефон. Здравствуйте, заказ 1204 не пришёл, звоните 8 (912) 555-12-34."
Входных токенов: ≈46 (грубая оценка без токенизатора, с запасом)
Модель: claude-sonnet-4-6 (цены на 2026-09-27), ответ до 512 токенов
  вход              $0.000138
  выход             $0.00768
  итого             $0.007818
  за 14 запросов    $0.109452
```

## Кэш промпта стоит по-другому

У Anthropic `input_tokens` в ответе не включает токены, записанные в кэш промпта и прочитанные из него: они приходят отдельными полями, запись дороже обычного входа, чтение в разы дешевле. `Usage.from_api` раскладывает поля как есть. Если в таблице у модели нет цены кэша, а такие токены есть, считать по цене обычного входа было бы враньём, поэтому программа останавливается с ошибкой.

## В формате OpenAI кэш посчитан наоборот

У Groq и OpenAI `prompt_tokens` уже включает токены, прочитанные из кэша, а их число лежит отдельно в `prompt_tokens_details.cached_tokens`. Если разложить это так же, как у Anthropic, кэш посчитался бы дважды: и по цене входа, и по цене кэша. Поэтому для этого формата отдельный `Usage.from_openai`, который вычитает кэш из входа, и тест на пример из документации Groq (4608 токенов из кэша). Токены рассуждений у моделей вроде gpt-oss входят в `completion_tokens` и оплачиваются как выход, отдельно их считать не нужно.

## Номер коммита в зависимостях у тех, кто подключает пакет

Если подключать token-counter из Гитхаба без номера коммита, обновление цен здесь тихо поменяет цифры в чужих отчётах. Поэтому в requirements.txt у проектов, которые его используют, стоит строка с номером коммита: `token-counter @ git+https://github.com/maarshir/token-counter@<коммит>`.
